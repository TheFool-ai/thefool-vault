## 双状态机诉求

**当前理解：客户原始材料希望把用户资格与目标计划进度融入路由、准入和恢复，并集中维护规则。11-11 晚团队补充的交付方向是先识别意图，进入对应业务后再按实时状态判断能否办理。** 影响意图路由的状态可供总控消费；状态维护按业务权威来源、粒度及更新逻辑逐项分工。不能据此认定要另建全局状态机或主 Bot。

11-11 21:05–21:07，韩康明确双状态机文档“不是实际开发的依据”。以下状态表是原始材料的需求线索，具体守卫、迁移和例外必须对照真实场景与接口确认；并不表示客户取消了状态约束。[最新实施口径](https://applink.feishu.cn/client/chat/open?openChatId=oc_e92a80a9064b44b9bd5e2174d38ffe58&position=276)

以下状态与准入规则来自[《状态机需求文档0828》](https://www.kdocs.cn/l/coVF7puoOnnh)第 2–5 章；实现边界结合[11-05 下午内部复盘逐字稿](https://bytedance.larkoffice.com/docx/R67cdsMYhogrlqxRrlRcyVL5nNd)和[11-10 架构方案](https://bytedance.larkoffice.com/wiki/U4vywWANniW6A8kRazact3Cjn4c)。

### 两个维度

| 维度 | 业务含义 | 关键状态 |
| --- | --- | --- |
| 用户状态 S | 这个用户已具备哪些资格、完成哪些业务前提，以及总体是否持有生效计划 | S0 未注册；S1 已注册；S2 核心画像健全；S3 已生成养老缺口；S4 商养开户有效；S5 风险测评有效；S6 已生成养老计划；S7 已交易、生效；S8 已退出为待定状态。 |
| 计划状态 P | 指定的这份养老计划办到哪里 | P0 草稿 → P1 方案确认 → P2 核保通过 → P3 支付中 → P4 支付成功 → P5 签单生效；之后可进入 P6 变更，最终 P7 终止。核保、支付有全部/部分成功分支；变更有继续执行、增加定投、组合切换、新增年金等分支。 |

用户状态正文明确：S2、S3、S4、S5 等并非必须依次完成，会出现多种组合。**开户有效、风险测评有效、已有缺口等条件要分别判断，不能只用一个“最高阶段”代替。** 对资格组合和用户综合阶段如何存储，是实现时需要澄清的问题。

一个用户可以有多份计划，每份计划按 `zqslplanID` 独立流转。用户状态是用户属性与名下计划状态共同形成的综合视图。

### 原始材料中的准入规则

| 要调用的 Agent | 用户条件 | 目标计划条件 |
| --- | --- | --- |
| 运营 | S1 已注册 | 无 |
| 规划 | S2 核心画像健全 | 无；“有历史缺口但画像不全”的例外尚有批注待确认 |
| 配置 | S3 + S4 + S5 同时满足 | 准入表未另列计划条件；新建计划另受在途计划约束 |
| 交易 | S3 + S4 + S5 同时满足 | P1 方案已确认 |
| 投后监控 | S7 已交易 | 表中未另列计划条件；具体操作仍需选择目标计划并判断其状态 |

这里的表是 **Agent 进入条件**，并未枚举每个 Agent 内部全部动作。核保、支付、变更、终止仍有更细的业务流程与校验。

几个必须覆盖的场景：

- **用户说“直接帮我买”**：意图可以识别为交易；未开户、测评失效或方案未确认时仍需拦截，说明缺什么并引导补齐。
- **开户或测评跳到 H5 后返回**：重新查询实际结果，通过后才更新资格。打开页面、用户口头说办完，都不能作为业务完成的依据。
- **老用户新建第二份计划**：已有计划 A 生效，用户仍为 S7；新计划 B 可从 P0 开始，不能用 A 的 P5 代替 B 的状态。文档限制同一用户不能同时有两份及以上计划处在 P0–P4。
- **终止其中一份计划**：A 到 P7，但 B 仍生效或变更中，用户仍为 S7；最后一份有效计划终止后的用户退出口径待确认。
- **流程中断再进入**：读取持久化的最新业务状态继续。会话记忆承接上下文，业务数据库及接口结果承接状态事实。
- **异步结果到达**：支付成功与签单生效分开；文档将 P5 的数据来源标为自营 T+1，11-05 批注要求账户中心定时批量推送，不能将所有环节理解成同步返回。

## Agent Graph 适配判断

AI 判断（2026-11-11）：[Agent Graph](https://github.com/context4ai/agent-graph/blob/main/README.zh-CN.md)适合承接业务步骤的合法路由、Agent 工作规程和完成证据；完整状态管控还需要业务状态服务、执行边界及规则管理。当前为选型建议，未形成团队决定。

具体候选设计：[新建计划 Agent Graph 方案](国民养老新建计划AgentGraph/方案.md)，含准备至 P1、交易至 P5、Facts/证据、宿主与规则职责、恢复路径和可校验的契约样例。

- **适配点**：材料已列出一批准入条件，正式口径仍需场景/API 核验。步骤内部需要对话澄清、解释和调用工具，且开户、确认方案、支付、签单都有外部证据。可按事实选择下一步，事实未更新时不把流程当作已推进。
- **建模方式**：用户资格、目标计划状态、当前意图、状态新鲜度、规则版本作为 Facts；业务步骤作为图节点。复用稳定图，运行按用户、目标计划和办理实例隔离。不要把所有 S×P 组合展开成独立节点。
- **规则分工**：简单条件可用图的 `requiresFacts` 表达；复杂、跨 Agent 复用的准入规则放统一规则服务，裁决结果及依据作为 Facts。图选择补资料、开户/测评、生成方案、确认、交易或等待结果等路线。
- **执行边界**：Host / 业务 API 必须在实际写入或提交交易前重新校验实时资格、目标计划、方案版本、用户确认与规则版本，并落实幂等、并发控制和审计。Graph 的合法 Route 本身不授予业务操作权限；Run 记录也不代替真实状态库。
- **产品缺口**：文件化、版本化 Graph 有利于工程维护和路由测试；运营人员使用的规则编辑界面、全局规则目录、发布审批和影响分析仍需另建或集成，不能把这些算作现成能力。
- **11-11 晚修正**：Graph 是选定办理意图后的业务流程候选。用户只是查计划或问产品时，不因账户/测评缺失而强行启动补齐流程。P0/P1 触发、P0–P4 单在途及 S3/S4/S5 守卫仍是待验证的建模假设；图与路由测试不等于客户验收。

建议先验证“新建一份计划 → 用户确认 → 允许进入交易”这一段。重点看：开户/测评不满足、H5 中断恢复、确认后方案变更、两份计划并存、重复回调、支付后等待签单等情况下，是否选中正确路线且实际业务调用无法绕过守卫。若只需给现有 Agent 加统一放行/拦截接口，先做规则服务即可；需要表达多步协作、完成证据与恢复时，再引入 Graph。

来源：[本库 Agent Graph 判断](../../../40-Resources/LLM%20Wiki.md#agent-graph-的核心价值)、官方[接入边界](https://github.com/context4ai/agent-graph/blob/main/docs/zh-CN/adoption-paths.md)、[事实与节点约束](https://github.com/context4ai/agent-graph/blob/main/docs/zh-CN/authoring.md)、[运行与恢复](https://github.com/context4ai/agent-graph/blob/main/docs/zh-CN/runtime-and-recovery.md)。

## 11-02：本体能力的初始分歧

- **现有能力**：生成 Schema → 抽取实例、生成图谱 → 包装为 Skill，供 Agent 按需调用。Agent 先有自己的执行逻辑，本体是其中一条知识调用路径。GraphRAG 知识召回在会上被判断为可支持。
- **FDE 对客户需求的理解**：由本体定义决策规则、分支和动作，Agent 反复读取本体来决定下一步，再执行工具、更新实例与关系。两层会有大量实时或准实时交互，高度依赖 Action Types 和 Logic Binding。
- **需求理解待客户确认**：上述全链路架构是蔡颖馨根据客户材料和况客设计作出的判断。客户是否一定要求强绑定本体，尚未确认。

蔡颖馨举的例子：养老金配置 Agent 接收用户参数和画像 → 本体判断下一步 → Agent 调用养老金试算工具 → 更新本体实例、关系 → 返回配置方案。具体推荐逻辑是明确规则，还是从历史案例推导，仍待调研。

## 实施备选路径

11-02 会中讨论了三类路径，当时尚未选定最终方案，需要与客户、况客对齐：

1. **等产品能力**：如果客户坚持本体驱动主链路，前期先与况客梳理一个核心场景的建模、规则和交互关系。会上估计单个场景可用约一个月梳理，Agent 落地依赖本体建模和产品上线。
2. **先用代码实现规则**：由况客用判断网关、硬代码跑通主链路，重点场景后续再接本体。客户是否接受待确认，也要说明采用本体的必要性。
3. **先落地现有能力**：选一个 Agent 的具体节点，如画像生成，验证本体 Skill 是否适用；若有知识召回需求，也可使用知识引擎现有能力。需调研调用的知识类型并取得客户认可。
