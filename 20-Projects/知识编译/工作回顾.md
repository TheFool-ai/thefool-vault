## 关键技术积累

- **架构边界**：以“Agent 生产内容、工程系统管理资产”划分空间、资产、编译任务、Agent Runtime、定时任务等模块。[概要设计](https://bytedance.larkoffice.com/wiki/CFtuwQT4ji31pOkfUtFcpslSn4f)
- **Agent 定义与执行分离**：用提示词、工具、Skill、Hook 声明组合不同 Agent，复用统一执行链路。
- **会话持续编译**：运行前加载历史上下文，执行中流式推进并按需压缩，执行后持久化消息和结果，支持大文件、多文件场景。
- **工作区到业务产物**：持久化中间文件，将生成结果登记为可管理产物，通过卡片展示，再衔接发布与消费。
- **组件适配**：用适配器隔离 VFS、图存储、沙箱差异，处理鉴权和请求入口差异，兼顾 SaaS 与私有化。
- **通用 Agent 接入**：复用开放平台换票机制传递身份与权限，提供 CLI / Skill。豆包工作中能力较多时，改用专门伙伴与预置提示词收敛适用场景和流程。

会话共享、隔离的具体机制继续按[专利选题中的核心积累](专利推进.md#我明确的核心积累11-06)讨论；述职正文明确了会话生命周期与工作区管理，结构细节见原方案。

## 我的方向判断与复盘

以下是我在 10-26 述职中的个人判断：

- 知识编译通过预加工和索引形成便于消费的知识形态。可靠知识底座是企业 Agent、数字员工落地的前提。
- 未来可能由“通用 Agent + 垂类知识 + 垂直系统”占据垂类 Agent 的生态位，垂类知识的重要性会进一步提高。
- 自然语言 SOP 需要“两次编译”：形成支撑决策的推理链，再形成支撑落地的可执行动作。
- 从 SaaS 开发转向 ToB 后，我开始直接面对部署环境和客户使用问题，对产品的理解从功能实现延伸到交付与使用。
- 自我复盘中，我认可快速落地、主动推进和表达方向判断；希望补齐 k8s 体系与无 AI 环境下的独立排障能力，沉淀客户交付中的共性问题与 SOP。
