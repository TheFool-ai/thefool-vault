## 11-02 对齐的方向

- **先验证消费，再倒推编译产物。** 李彦享介绍的是消费侧推理 POC：用编译好的 Schema、公理、规则等跑通推理，反过来确定编译应输出什么。编译端完整链路仍待实现。（00:20）
- **定义与实例分开。** POC 用 TTL 表达定义和规则；实例仍放 TuGraph，按任务提取相关数据进入推理上下文。自定义 JSON 与 TTL 如何转换、最终产物协议待定。
- **能力关联到对象类型。** 在 Schema 图的对象详情里展示属性、公理、约束、规则和 Action；保留各自名称，不为简化交互把它们全部合并成“关系”。（1:01–1:09）
- **自然语言与正式表达结合。** 用户用自然语言查看、修改，底层转换为引擎可消费的表达；允许查看正文。对象详情与审阅方式结合，具体交互还需细化。（1:06–1:09）
- **推理引擎要能被用户感知。** 输出应带出所用规则、证据和推导结果，先用文字解释，不要求专门画推理网络图。（1:09–1:11）
- **术语消歧复用现有术语库。** 消费端优先使用知识引擎术语库，将业务别名对应到本体对象或实例；需要与消费入口联动。（41:33）

## 能力缺口

以下是会议讨论的建设范围，尚未逐项承诺交付。

| 方向 | 需要补齐什么 |
| --- | --- |
| 一致性校验 | Schema 保存或发布时发现继承环、关系和属性约束冲突；导入错误要可见，能定位并修正 |
| 抽取、融合与消歧 | 展示抽取来源、实体合并与规范化结果；基数冲突、跨文档属性冲突进入审阅，保留冲突和处理选择 |
| 标准交换与版本 | 支持标准格式导入导出；定义与实例的格式和规模限制分别确定；版本间 Schema 差异及实例统计如何展示待定 |
| 推理与优化 | 事实推导、假设条件变化、多约束决策与优化；结果附证据和规则依据 |
| Action 与人机协同 | 动作注册、计划到工作流的协议、执行前检查、权限、风险等级、自动执行或人工确认、执行结果 |
| 反馈与消费侧能力 | 用户反馈回流、术语沉淀、模型自动选择等要求；现有能力和最小接法待核对 |

不能把已有的局部检查算作完整冲突处理：会上提到目前有类型和基数提示，但跨文档事实冲突识别仍有缺口。实例导出用 TTL 还是 CSV、是否按数量分流，以及实例全量版本比较，都只是讨论方案。

## 消费链路与验证场景

会上讨论的目标链路，推理侧已有 POC 探索，Action 接入待实现：

> 用户问题 → Agent 找到相关对象与实例 → 推理、校验或优化引擎 → 决策方案与依据 → 按需确认 → Action 执行。

示例是中石油加油站便利店商品试销：判断商品能否在某站试销，再考虑预算、采购量等约束。另讨论了关系链推导和带条件的座位分配，测评用例尚未最终收敛。

推理、数据校验和数值约束优化需要分别验证。会上讨论了推理工具包和 Z3 等候选工具，生产选型、部署和高可用方案待定。

消费入口讨论过互动助手、SOP Agent 和开发机执行 Agent。费夕杨倾向先快速接一个 Demo，尽量复用现有能力；最后仍发现 Action、权限和人机协同存在能力缺口，接入方案和开发边界未定。（1:11–1:15）

Action 执行涉及陈浩津侧的 dynamic workflow。动作注册、权限元数据和执行协议需要双方对齐；会上倾向由目标业务系统负责最终权限校验，消费侧可先做检查。

AI 补充的设计问题：生成计划后，执行时状态和权限是否仍满足，需要在方案中明确。

## 11-05：知识编译与索引层

**我的判断：** “知识编译的核心价值就在于在索引层做工”。我认为[这篇公众号文章](https://mp.weixin.qq.com/s/4n25-4mUOEg2wn5MB1iXyQ)很符合之前的认知，想深入讨论知识编译到底是什么样子。

**文章观点：** 作者张颖峰，InfiniFlow，2026-11-05；正文由我在对话中提供。

- Search Harness 编排查询时的探索，知识编译提前加工可复用的上下文，二者通过工具接口协同。
- 同一份原文可编译成导航、关系、时间线、Wiki 和原子命题等视图。作者称单独构建目录树未必有效，当前主要收益来自带逐字证据的 Claim/Evidence 单元。
- 模板规定抽取对象、字段、约束和输出；本体是其中一种模板，按 TBox 抽取 ABox，为搜索提供扩展与约束。
- 产物携带来源与血缘；正文检索与派生产物通道分开。作者描述的重建策略是幂等整体重算，不能据此认定已具备细粒度增量编译。
- Token 节约和基准表现为作者报告，实验口径与复现结果未核实。

**AI 提出的讨论判断，尚未确认：**

- 可先把知识编译理解为：在索引阶段生成带来源、可维护、可被工具消费的知识表示。Wiki、图谱和本体是不同产物，具体选择由消费任务倒推。
- 共用实体、来源和依赖信息，再按需生成不同视图，是候选设计；不必强制所有产物都经过图谱。
- 命题压缩需要保留范围、时间、例外和规则效力。引用能定位到原文，只保证来源可追溯；原文是否支持命题、命题是否足以回答问题，需要另行判断。
- 面向问答的上下文供给，与规则校验、推理和 Action 消费应分别明确契约。文章中的本体定位不能直接覆盖项目的业务执行目标。

下一步讨论：选一个真实消费任务，定义必要产物、读取工具、回源条件和更新策略，再与原文加 Search/Grep 的基线比较。尚未形成具体方案。
